# TransPay — Phase 1

> **Reviewers:** this is the repository for the Instawards Statement of Work
> *"TransPay — USD to PHP Transfer Order"*, Phase 1, built by a single
> full-stack builder. The repository is published under this name, which differs
> from the placeholder URL printed in the submitted SOW — if you arrived from
> that document, you are in the right place.

A remittance **prototype**: a chat-style interface that takes a USD → PHP
transfer order through quote, confirmation and recipient capture, and then
settles the corresponding value as a real USDC transaction on the **Stellar
Testnet**, with the order's reference ID written into the transaction memo so
the payment proves for itself which order it belongs to.

**Everything that was delivered can be checked from one file:**

> ### → [`evidence/INDEX.md`](evidence/INDEX.md)

That file is generated by the two evidence scripts and links to the newest run
of each deliverable:

| Deliverable | What it shows | Result of the latest run |
| --- | --- | --- |
| **D1** | 10 transfer orders created through the USD → PHP flow, each with a different amount and different recipient bank details | **10 / 10 passed** |
| **D2 · positive** | 10 **real** USDC transactions on Stellar Testnet, each hash bound to its order via the memo | **10 / 10 passed** |
| **D2 · negative** | 5 invalid deposits (3 duplicate references, 2 mismatched amount/order) that must be rejected without producing any transaction | **5 / 5 rejected, 0 transactions produced** |

The two figures are deliberately **not** added together: a rejected case is
stopped before any transaction is built, so it cannot have a transaction hash
and is not part of the positive group's 10/10.

Nothing in the evidence pack is typed by hand. Re-running the scripts
regenerates every table, so a bug fix costs a re-run rather than an afternoon of
screenshots.

## 1. What this is — and what it is **not**

**It is** a technical prototype that proves one specific thing end to end: a
transfer order can be created, quoted, confirmed, and then bound to a real
blockchain settlement that anyone can independently verify.

**It is not:**

- **Not a money transmission service.** Nobody's money moves. There is no
  licence, no payment institution, no counterparty.
- **Not a WhatsApp or Messenger integration.** The chat interface is a
  **simulated UI** built into the web app. It looks like a messaging thread
  because that is the intended end-user experience, but it is not connected to
  any messaging platform.
- **Not on a live blockchain network.** Settlement happens exclusively on the
  **Stellar Testnet**, using test USDC that has no monetary value. Mainnet is
  blocked in code, not by convention: the app refuses to start unless
  `STELLAR_NETWORK=testnet`.
- **No real payout.** No peso ever reaches a Philippine bank account. The
  "payout" is a transfer between two accounts we control on the test network,
  and the recipient bank details in the evidence are fabricated test data.
- **No KYC, no sanctions screening, no compliance workflow.**
- **The FX rate is a fixed placeholder** (1 USD = 56.50 PHP, 1% fee). Phase 1
  calls no market rate provider. The number is fixed on purpose so that ten
  runs produce reproducible figures.
- **No sender-facing money-in.** The USD deposit is a *simulated* reference
  code. Confirming it is a trigger, not a payment.

## 2. Verify one settlement yourself — 5 minutes, no trust required

You do not have to believe our database. Here is why, and how to check it.

1. **Open the results table.** Go to
   [`evidence/INDEX.md`](evidence/INDEX.md) and click the newest **D2** link.
   That opens `d2-summary.md`, which starts with the positive group's table.
2. **Pick any row** — row 1 is fine — and note two things from it: the
   **`Reference ID`** (looks like `TP-PHP-20260903-0148`) and the **`Stellar
   Expert`** link.
3. **Open the Stellar Expert link.** It goes to the public block explorer for
   the Stellar Testnet, a site we do not control. If you prefer, take the full
   transaction hash from the *Local originals* table just below and paste it
   into `https://stellar.expert/explorer/testnet/tx/<hash>`.
4. **Find the `Memo` field on that page and compare it with the `Reference
   ID`** from step 2. They must be identical.
5. Optionally, check that the amount matches the `USDC settled` column and that
   the destination is the payout float account listed at the top of the
   summary.

**Why step 4 is the whole point.** The memo is written into the transaction at
signing time and is then stored on the public ledger, forever, outside our
control. It is the one place where a payment states which order it belongs to
without going through us. If the memo on the ledger equals the reference ID in
the table, that transaction belongs to that order — regardless of what our
database says.

### Check all ten at once, in one step

There is an even shorter check that covers the whole set. Open the payout float
account on the block explorer:

**<https://stellar.expert/explorer/testnet/account/GCQQLXJEP3DRCNY6JYUMYAR7BM6WU34XG42W2BPSYPVMORTTVY3VMPK3>**

Read its USDC balance and compare it with the total of the `USDC settled` column
in the results table. They must be identical — currently **`730.1250000`**.

This account was created for this delivery and **started at exactly zero**, so it
has received nothing except the settlements in this report. That makes the number
on the explorer a complete, independent audit of the set: if any transaction in
the table were invented, or any real transaction were left out of it, the balance
would not agree. You do not need a "before" figure from us, and you do not need
to trust our database at all.

> If the balance you see does **not** match, check the top of `d2-summary.md`
> first. A run generated on a reused corridor carries a warning banner there
> saying so, and in that case the balance legitimately exceeds the table. A pack
> without that banner is claiming this check holds.

### After 16 December 2026 the links will be dead — and the evidence will not be

Stellar Testnet is reset periodically, and the reset scheduled for
**16 December 2026** wipes all Horizon history. From that date every Stellar
Expert link in this repository returns **404**, even though the work was
completed in October.

That is anticipated, and it is why each transaction is stored twice in
`evidence/d2/<run>/tx/`:

- **`<reference>.xdr`** — the raw signed transaction (the exact bytes that were
  signed and submitted). Hashing it reproduces the transaction hash in the
  table.
- **`<reference>.horizon.json`** — the complete JSON that Horizon returned when
  the transaction was confirmed, including ledger sequence, timestamp, memo,
  source and destination accounts, and amount — plus the same fields as
  recorded in our database, side by side.

These are the network-independent originals. To re-check the whole pack with
**no internet and no database**:

```bash
npx tsx scripts/verify-evidence.ts
```

That script re-derives each transaction hash from the stored signed bytes and
cross-checks the memo, amount, asset, source and destination between the XDR
and the stored Horizon JSON. It prints a table and fails loudly on any
mismatch.

## 3. Running it from scratch

Prerequisites: Node.js 20+, `pnpm`, and Docker (for PostgreSQL).

```bash
docker compose up -d        # PostgreSQL on localhost:5434
pnpm install
pnpm db:migrate             # create the schema
pnpm stellar:bootstrap      # create the Testnet corridor accounts (see below)
```

`pnpm stellar:bootstrap` creates three Testnet accounts (issuer, treasury,
payout), funds them from Friendbot, opens the USDC trustlines and issues
100,000 test USDC to the treasury. It prints the values to paste into `.env`
and also writes every secret to `.env.secrets`. **Run it once.** If the
accounts already exist, do not run it again — you would create a new corridor
and orphan the existing evidence.

If you are setting up more than one environment, run it once **per
environment** and give each its own secrets file:

```bash
BOOTSTRAP_VAULT=.env.secrets.production pnpm stellar:bootstrap
```

Each environment needs its own corridor — never point two environments at one
treasury. Limitation 5 explains why, and what broke when that rule was ignored.

Then, in two terminals:

```bash
pnpm dev                    # web app on http://localhost:3000
pnpm worker                 # settlement worker
```

And to regenerate the evidence pack:

```bash
pnpm evidence:d1            # 10 transfer orders, no ledger activity
pnpm evidence:d2            # 10 real Testnet transactions + 5 rejections
```

**Stop `pnpm worker` before running `pnpm evidence:d2`.** The evidence script
runs the *same* settlement code the worker runs, so two of them at once are two
processes competing for the treasury's transaction sequence. A database advisory
lock prevents that from producing a double payment, but the run will be slower
and harder to read. One at a time.

Each evidence run writes its own new timestamped folder and rewrites
`evidence/INDEX.md`, which always points at the newest run. Nothing is
overwritten in place, so re-running never destroys an earlier result. The
repository currently ships one run of each deliverable.

`pnpm test` (138 tests) and `pnpm typecheck` should both be clean.

### An evidence corridor is single-use per handover

**Read this before you re-run `pnpm evidence:d2` — this is the rule that is
easiest to break by accident.**

`pnpm evidence:d1` is free to run as often as you like: it touches no ledger.
`pnpm evidence:d2` is different. **Every handover needs a corridor that has
never been used before.** Concretely: before you hand a pack to anyone, run
`pnpm stellar:bootstrap`, point `.env` at the new issuer / treasury / payout,
and *then* run `pnpm evidence:d2`.

The reason is not tidiness. The strongest claim in this whole delivery is the
one-step check in section 2: *the payout float's balance on a public block
explorer equals the total of the results table, because that account has
received nothing else.* That sentence is only true while the payout float's
entire credit history is exactly the ten legs in that one report. Run D2 twice
against the same corridor and the ledger shows twenty credits and twice the
money while the table still shows ten — the pack's headline claim becomes false
even though nothing went wrong with any individual transaction.

This is a trap set for the middle of a sprint, because the natural workflow is
to fix a bug and re-run. It has already happened twice here: once by re-running
on a used corridor, and once when a deployed environment sharing the corridor
settled one test order into the payout float. Both times every internal check
stayed green and only the README was wrong.

So `pnpm evidence:d2` now checks the condition itself. If the payout float was
not empty when the run started, or if the number of credits on the ledger does
not equal the number of legs in the report, the run:

- prints a **`WARNING — THIS RUN IS NOT FIT FOR HANDOVER`** block naming the
  opening balance, the credit count, and the two totals that disagree;
- writes the same warning as a banner at the **top of `d2-summary.md`**, and
  replaces the one-step instructions with an explanation of why they do not
  apply, so a stale pack cannot look clean to a reviewer;
- records `handoverReady: false` in `run.json`, which makes the run show up as
  `FAIL` in `evidence/INDEX.md`;
- **exits non-zero.**

If you are mid-iteration and genuinely do not care yet, pass
`--allow-reused-corridor` (`pnpm evidence:d2 --allow-reused-corridor`). That
suppresses only the exit code. The console warning and the banner in the
published document are deliberately not suppressible.

All configuration is environment variables. Copy `.env.example` to `.env` and

| --- | --- | --- |
| `DATABASE_URL` | PostgreSQL connection string | `postgres://transpay:transpay@localhost:5434/transpay` |
| `STELLAR_NETWORK` | Hard-blocked to `testnet`. Any other value and the app refuses to start. | `testnet` |
| `STELLAR_HORIZON_URL` | Horizon API endpoint | `https://horizon-testnet.stellar.org` |
| `STELLAR_ASSET_CODE` | Settlement asset code | `USDC` |
| `STELLAR_USDC_ISSUER` | **Issuer of the test USDC — see the note below** | `GD3WPI6M3JVWL66FPNC5SAPTBF4SRFZ4VEBVYG22Q2EAVQFVH5WBH7HF` |
| `CORRIDOR_TREASURY_SECRET` | Secret key of the USD-side treasury; signs settlements | *(secret — not in this repo)* |
| `CORRIDOR_PAYOUT_PUBLIC` | Public key of the PHP-side payout float | `GCQQLXJEP3DRCNY6JYUMYAR7BM6WU34XG42W2BPSYPVMORTTVY3VMPK3` |
| `SETTLEMENT_POLL_INTERVAL_MS` | Worker scan interval | `3000` |
| `SETTLEMENT_TIMEBOUNDS_SEC` | Validity window of a settlement transaction | `180` |

### The Testnet USDC issuer is not a well-known address

On mainnet, USDC has one canonical issuer that everybody recognises. **On
Testnet it does not.** Testnet has no standing USDC, so `pnpm stellar:bootstrap`
creates its own issuer account and issues test USDC from it. Any asset called
"USDC" on Testnet is only meaningful together with its issuer address.

The issuer behind every transaction in this evidence pack is:

```
GD3WPI6M3JVWL66FPNC5SAPTBF4SRFZ4VEBVYG22Q2EAVQFVH5WBH7HF
```

It is stated here so nobody has to guess. It also appears in every
`tx/<reference>.horizon.json` file and in `d2-positive.csv`. If you re-run
`pnpm stellar:bootstrap`, you get a *different* issuer and a different corridor,
and the previously generated evidence will refer to the old one.

### Secrets

`pnpm stellar:bootstrap` writes all generated secret keys to **`.env.secrets`**
(file mode `600`). That file is listed in `.gitignore` and is **never
committed**. The application itself does not read it — the app only ever signs
with `CORRIDOR_TREASURY_SECRET` from `.env`, which is also gitignored.
`.env.secrets` exists so the issuer and payout keys are not lost when the
console scrollback disappears; the issuer key is needed to mint more test USDC,
and the payout key to sweep the float.

The evidence scripts refuse to write a file that contains a Stellar secret seed
or an order access token: every byte is scanned before it hits disk, and the run
aborts rather than emit a leaked value.

## 5. The two corridor accounts are two different roles

```
   USD side  (collection)                          PHP side  (distribution)
   ──────────────────────                          ───────────────────────
   treasury                                        payout float
   GALWUJLF…QH4U4CBX                               GCQQLXJE…TVY3VMPK3
        │                                                    ▲
        │   USDC payment · memo = the order's reference ID   │
        └────────────────────────────────────────────────────┘

   "the sender's USD has been received"     "value is now available to pay
                                             pesos to the recipient locally"
```

A remittance corridor has two sides. On the collection side, a treasury account
holds the value backing USD that senders have paid in. On the distribution side,
a payout float holds the value that the local partner draws on to pay pesos to
recipients. A settlement moves value **from the collection side to the
distribution side** — that is the transfer being modelled, and in a production
corridor the two sides are two different institutions in two different
countries.

**This is not one account paying itself to manufacture a transaction hash.** The
two accounts have different keys, hold separate balances, and play opposite roles
in the corridor: the treasury is always the source and the payout float is always
the destination. The asymmetry is visible on the public ledger — across the ten
legs of the latest run the treasury fell from `100000.0000000` to `99269.8750000`
USDC while the payout float rose from `0.0000000` to `730.1250000`, the same
`730.1250000` recorded in the database.

What Phase 1 does **not** model is the last mile: converting that value into
pesos and crediting a real bank account. That is out of scope, and the payout
float is a test account we control, not a partner's account.

## 6. Known limitations of Phase 1

Stated plainly rather than left for you to find. None of these is a bug we have
not noticed; each is a scope decision or a known gap with a known fix.

1. **The order-creation API has no authentication and no rate limiting.**
   `POST /api/orders` is open: anyone who can reach the server can create
   unlimited orders and consume reference-ID sequence numbers. Acceptable for a
   local prototype, not acceptable for anything reachable from the internet.

2. **The access token travels in the URL.** Every step after creation is
   addressed as `/api/orders/<token>/…`, so the token is written into HTTP
   access logs, proxy logs and browser history. Anyone with log access can read
   another sender's order. The token is deliberately kept out of the ledger
   memo, out of application logs and out of the evidence pack, but the URL is a
   real leak path. It should move to a header or a cookie.

3. **Expired quotes are never swept.** A quote is valid for 15 minutes and the
   expiry is enforced at the moment someone tries to confirm it — but no
   background job moves stale orders to `expired`. An abandoned order sits in
   `quoted` indefinitely and looks pending when it is not. (You can see one such
   row in the database from an early smoke test.)

4. **The worker's advisory lock breaks silently behind a transaction-mode
   connection pooler.** Only one process may submit settlements at a time,
   because all settlements share the treasury's transaction sequence. That is
   enforced with a PostgreSQL *session-level* advisory lock held on a dedicated
   connection. Put pgBouncer in `transaction` pooling mode in front of the
   database and the lock is acquired on one backend and released on another —
   it stops protecting anything, **without any error being raised**. Two worker
   instances would then race for the sequence. Deploy the worker with a direct
   connection, or a session-mode pooler, or replace the advisory lock with a
   row-level lock. This is one of *two* ways the lock can fail to protect you —
   the other is running two environments against two different databases, which
   is limitation 5.

5. **The evidence corridor must not be shared with any other environment, and
   the worker's lock cannot enforce that.** This is the limitation to read if you
   intend to deploy this yourself.

   The deployed app on Railway uses a **completely separate corridor** — its own
   issuer, treasury and payout float — from the one that generates this evidence.
   That separation is mandatory, for two independent reasons:

   - **Correctness.** Every settlement is signed by the same treasury account, so
     they all draw on that account's single transaction sequence number. Only one
     process may submit at a time. That constraint is enforced with a PostgreSQL
     advisory lock — but **an advisory lock is scoped to the database it is taken
     in.** Production runs against Railway Postgres and local runs against local
     Postgres, so a lock held in one is completely invisible to the other. Two
     workers in two environments signing from one treasury would therefore race
     for the sequence number with nothing stopping them, and one would fail with
     `tx_bad_seq`. The lock protects against a second worker on the *same*
     database; it can do nothing about a second worker on a different one. If you
     run more than one environment, give each its own treasury — do not rely on
     the lock. (Limitation 4 above is the other way this lock can silently stop
     protecting you, for an unrelated reason.)
   - **Evidence integrity.** The payout float's balance is the strongest claim in
     this delivery precisely because that account has received nothing except the
     settlements listed in the report. A single transaction from another
     environment breaks that claim permanently. This is not hypothetical: it
     already happened. One test order on the deployed app settled `42.0750000`
     USDC into the account a previous evidence pack was using, and the absolute
     reconciliation broke — ledger `772.2000000` against `730.1250000` in the
     database. It could not be patched by sending the money back, because a
     refund is itself another operation in that account's history and would
     equally falsify "this account received nothing else". The only honest fix
     was a new corridor, which is why `pnpm stellar:bootstrap` now takes a
     `BOOTSTRAP_VAULT` variable so each environment writes its own secrets file.

6. **Three earlier corridors were retired, and their history is still in the
   database.** The first was replaced because its keys were exposed outside
   `.env.secrets`; the second because of the cross-environment contamination
   described above; the third because it had already been used for a previous
   pack (limitation 7). Test keys carry no monetary value, but anyone holding an
   old treasury key can submit transactions from that account, and an account's
   history *is* the evidence for D2 — so a retired corridor is never reused.
   Consequences worth knowing:

   - The retired corridors' 53 settlement legs are still in the database and
     still on-chain. They are excluded from the evidence tables by destination
     account **and** asset issuer — filtered out, never deleted. That pairing
     matters: one retired corridor totals exactly the same `730.1250000` as the
     current one and another totals exactly double it, so filtering on amounts or
     leg counts would be ambiguous where filtering on the account pair is not.
   - Every Stellar address quoted anywhere in this repository is a **current**
     corridor address.
   - The upside of starting over: the current payout float began at **exactly
     zero**, which is what makes the strongest reconciliation possible. The very
     first corridor could only be reconciled on the change in balance, because it
     had already received test USDC before the database existed.

7. **The evidence pack must be regenerated on a fresh corridor for every
   handover, and that is a manual step.** The one-step check in section 2 holds
   only while the payout float has received nothing but the settlements in the
   report it accompanies, so an evidence corridor is single-use. `pnpm
   evidence:d2` detects a reused corridor, warns in the console, stamps a
   warning banner on `d2-summary.md`, marks the run `FAIL` in the index and
   exits non-zero — but it cannot create the new corridor for you. Someone has
   to run `pnpm stellar:bootstrap` and update `.env`. See the end of section 3
   for the full procedure.

8. **Recipient account numbers appear in clear text in the evidence CSVs.** They
   are fabricated test values, so nothing real is exposed, but the same script
   pointed at real recipients would need to mask them.

9. **One settlement attempt is not retried forever.** A leg that misses its
   180-second validity window is retried with a fresh transaction, up to 3
   attempts, after which the order is rejected for a human to look at. Money
   cannot be sent twice — the money never left the wallet in that scenario — but
   there is no operator alerting.

## 7. The order lifecycle

```
  draft
    │   quote issued (rate, fee, PHP estimate, 15-minute expiry)
    ▼
  quoted ─────────────────────────────────────┐
    │   the sender confirms the quote         │
    ▼                                         │   abandoned before
  confirmed ──────────────────────────────────┤   the quote ran out
    │   recipient name / bank / account       │
    ▼                                         │
  recipient_added ────────────────────────────┤
    │   simulated USD deposit reference       │
    ▼                                         │
  awaiting_deposit ───────────────────────────┴──▶  expired     (terminal)
    │       │
    │       └─────────────────────────────────┐
    │   deposit reference confirmed           │
    ▼                                         │   duplicate deposit reference,
  settlement_ready ───────────────────────────┤   mismatched amount or order,
    │   transaction built, signed, hash       │   permanently failed settlement
    │   written to the database, submitted    │
    ▼                                         │
  settling ───────────────────────────────────┴──▶  rejected    (terminal)
    │
    │   ★ only here: the LEDGER confirms the transaction
    ▼
  settled   (terminal)
```

| State | Meaning |
| --- | --- |
| `draft` | An order exists but has no quote yet. |
| `quoted` | Rate, fee and PHP estimate issued, valid 15 minutes. |
| `confirmed` | **The sender accepted the quote.** |
| `recipient_added` | Recipient name, bank and account captured. |
| `awaiting_deposit` | A (simulated) USD deposit reference has been issued. |
| `settlement_ready` | The deposit reference was confirmed. The worker may now pick this order up. |
| `settling` | A settlement transaction has been built, signed, recorded, and submitted. |
| `settled` | **The ledger confirmed the transaction.** Terminal. |
| `rejected` | Refused — duplicate deposit reference, mismatched amount or order, or a permanently failed settlement. Terminal. |
| `expired` | Abandoned before the quote ran out. Terminal. |

### Why only the ledger can move an order from `settling` to `settled`

Because `settled` is a claim about the outside world, and only the outside world
can confirm it.

Every other transition is a decision our own system makes and can therefore
record with confidence. `settled` is different: it asserts that a payment
actually exists on a public ledger. Our application cannot know that by having
tried — a network timeout looks exactly like a success from the sender's side.
So the code takes the one route that cannot lie: it writes the transaction hash
to the database *before* submitting anything, then asks Horizon a single
question — *is this hash in a ledger?* — and only a confirmed **yes** flips the
order to `settled`, in the same database transaction that marks the settlement
confirmed.

The consequence is the property that makes the evidence in this repository worth
reading: an order marked `settled` has a transaction hash that a stranger can
look up, and a memo on that transaction that ties it back to the order. If the
ledger has not confirmed it, the order is not settled — no matter what our code
thought had happened.
